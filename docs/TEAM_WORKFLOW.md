# 팀 작업 가이드

두 사람이 각각 구현과 리뷰를 주도하고, 필요한 작업마다 Claude와 Codex를 선택한다. 앱을 개발하는 AI 도구 선택과 센터 PC 내부에서 실행하는 로컬 분석 모델 설정은 독립적이다.

## 처음 클론하고 시작하기

GitHub Collaborator 초대를 수락한 뒤 자기 계정으로 저장소를 클론한다. 각 PC에서 `main`은 최신 통합본을 확인하는 데 사용한다. 이 가이드가 포함된 PR을 검토하는 동안에는 GitHub PR의 작업 브랜치를 사용한다.

```powershell
git clone https://github.com/ksh0330/JeJuOneEyes.git
cd JeJuOneEyes
git switch main
git pull --ff-only origin main
```

- 폴더를 Codex 앱에서 Local 프로젝트로 열거나, 그 폴더에서 `codex`를 실행한다. Claude Code는 작업 경로에서 `claude`를 실행한다. [AGENTS.md](../AGENTS.md)가 팀 공통 지침이며, [CLAUDE.md](../CLAUDE.md)가 이를 불러온다. 채팅에 전체 기획을 반복해서 붙여넣을 필요 없이, 아래 역할 프롬프트에 이번 작업을 추가한다. [Codex 프로젝트 지침](https://learn.chatgpt.com/docs/agent-configuration/agents-md) · [Claude Code 메모리](https://code.claude.com/docs/en/memory)
- 첫 구현은 Python 3.11을 개발 환경 후보로 잡고, 실제로 설치한 버전과 패키지 목록, 실행 명령을 README에 적는다. 각자 `.venv`를 만들어 같은 버전으로 설치한다. 모델은 선택한 로컬 런타임의 동일한 파일과 버전을 쓴다. 개인 데이터 경로와 모델 경로는 `.env` 또는 구현이 정한 로컬 설정에서 지정한다. 설정 키를 코드에 넣는 PR이 같은 변경에서 사용법과 값 없는 `.env.example`을 추가한다.
- 재현에 쓸 공개 파일은 [제주데이터허브 상권분석 매쉬업](https://jejudatahub.net/data/view/data/748)에서 `_19.csv` 파일을 준비한다. 센터 데이터와 첨부 엑셀은 각자 이용 권한이 있는 경로에 둔다. 팀 공유용 PR에는 코드, 공유가 허용된 정제 스키마, 공개 또는 합성 검증용 예시만 포함한다. 클라우드 에이전트에 줄 입력도 같은 범위로 제한한다.

## 작업을 겹치지 않게 나누기

작업을 열 때 PR 또는 이슈에 **담당자, 브랜치, 변경 경로, 의존하는 PR, 완료 기준**을 한 줄씩 남긴다. 각자 PC에서 작업하면 각각 클론이면 충분하다. 같은 PC에서 두 구현을 병행할 때만 작업별 worktree가 유용하다.

| 작업 | 작업 브랜치 예 | 담당 경로 |
| --- | --- | --- |
| 데이터·카탈로그·검산 | `feat/market-analyzer` | `core/connectors/`, `core/kg/`, `core/analyzer/`, 관련 `tests/` |
| 플래너·화면 | `feat/analysis-ui` | `core/planner/`, `app/`, 관련 `tests/` |
| 공용 계약·통합 | `feat/integrate-analysis` | `contracts/`, 의존성·설정, 모듈 조립, 통합 시연 |
| 기획서·설명자료 | `docs/submission-materials` | `docs/` 안의 제출 관련 문서. 실제 시연 증거가 생기면 갱신한다. |

두 명 기준으로 데이터·검산과 플래너·화면을 먼저 나눈다. 둘 다 계약 예시를 사용해 먼저 작업할 수 있다. 경로가 겹치거나 공용 계약·의존성 변경이 필요하면 열린 PR을 확인하고 해당 변경을 한 담당자에게 모은다. 통합 담당이 두 모듈을 연결한다. 같은 PR에서 Claude가 편집 중이면 Codex는 읽기 전용으로 검토하고, 수정이 필요하면 같은 작성자가 이어서 반영하거나 편집 담당을 인계한다.

```powershell
git fetch origin
git switch -c feat/market-analyzer origin/main

# 같은 PC에서 다른 작업을 동시에 열 때는 별도 폴더를 만든다.
git worktree add -b feat/analysis-ui ../jeju-analysis-ui origin/main

# 작업 브랜치에서 커밋한 뒤
git push -u origin HEAD
```

GitHub에서 `main` 대상 PR을 열고 팀원이 검토한다. 검토한 변경을 병합한 뒤 다음 작업은 갱신된 `origin/main`에서 시작한다. 오래된 브랜치에 최신 통합본을 가져오려면 먼저 `git fetch origin`을 실행하고, 필요한 경우 작업 브랜치에서 `git merge origin/main`으로 충돌을 해결한다. 공유 브랜치에 강제 푸시하는 방식은 피한다.

## 모델과 추론 수준

이 표는 팀의 시작점이다. 각 도구에서 제공되는 모델과 수준으로 선택하고, 평소보다 높은 수준을 썼다면 결과에 영향을 준 경우만 PR에 남긴다.

| 작업 | 선택 위치 | 기본값과 높이는 경우 |
| --- | --- | --- |
| Claude 구현 | 작업 폴더의 Claude Code 채팅. `/model opus`, `/effort medium`부터 시작 | 모듈 구현은 Medium. 계약 설계, 여러 단계의 디버깅은 해당 모델에서 가능한 High. 문서 수정이나 작은 코드 변경은 빠른 모델이나 낮은 수준으로 충분하다. |
| Codex 리뷰·리팩토링 | Codex 앱의 모델 선택기 또는 CLI의 `/model`. 리뷰할 브랜치·PR을 지정 | GPT-6.2 Sol을 쓸 수 있으면 Medium. 다중 테이블 집계, 조인 검증, 재현이 어려운 버그는 High 또는 사용 가능한 상위 모델을 검토한다. 변경 없는 코드까지 전부 재검토할 필요는 없다. |
| Gemini 또는 Claude 문서 초안 | 해당 도구의 새 채팅에 제출 계획과 공유 가능한 실행 증거만 전달 | Gemini Pro 계열 또는 Claude를 쓸 수 있다. 초안은 기본 추론에서 시작하고 여러 근거가 충돌할 때만 깊은 추론을 쓴다. 수치와 기능 범위는 최종적으로 사람이 실행 증거와 대조한다. |
| 제품 로컬 SLM | 구현에서 정한 로컬 모델 경로와 런타임 설정 | [공통 설계](ARCHITECTURE.md)의 실행 후보로 시작한다. 성능을 측정한 후 모델·양자화·런타임 버전을 고정한다. |

[Codex 모델 안내](https://learn.chatgpt.com/docs/models) · [Claude Code 모델 및 effort 설정](https://code.claude.com/docs/en/model-config#adjust-effort-level)

## 변경에 맞는 검증

| 변경 | 작성자가 먼저 할 검증 | 리뷰어가 더 확인할 경우 |
| --- | --- | --- |
| Markdown·문구 | 변경 내용과 링크 확인, `git diff --check` | 규칙, 구현 상태, 수치가 달라졌을 때 해당 근거만 확인 |
| 단일 모듈 코드 | 수정 기능에 해당하는 테스트 또는 짧은 실행 | 실패 경로가 재현되지 않았거나 변경 위험이 클 때 추가 재현 1~2개 |
| JSON 계약·데이터 해석·조인 | 예시 JSON 형식, 호출 모듈 사용 예시, 기준값 또는 결측·중복 사례 | 영향을 받는 경로만 확인. 대화 조건 보존, 누락과 관측값 0, 미검증 조인 차단 중 관련 항목을 선택 |
| 모듈 통합·최종 ZIP | 대표 흐름 한 번, 다른 PC나 깨끗한 환경에서 설치·실행, 포함 파일과 비밀값 점검 | 실행 결과·기획서·패키지 버전의 차이가 있을 때만 해당 흐름 재실행 |

PR 검토를 요청하기 전에 변경 범위에 필요한 항목만 확인하고, 실행한 명령과 결과를 PR에 남긴다. 리뷰어는 그 기록을 재사용한다. 수행하지 못한 검증은 사유를 한 줄로 기록한다. 전체 시연은 모듈 통합과 제출 시점에 실행한다.

## 복사해서 쓰는 시작 프롬프트

### Claude 구현 또는 Codex 구현

```text
AGENTS.md, docs/ARCHITECTURE.md, docs/TEAM_WORKFLOW.md를 읽어줘.
작업은 [목표], 브랜치는 [브랜치], 수정 경로는 [경로]야.
현재 브랜치와 열린 PR의 경로를 확인하고, 관련 JSON 계약과 예시를 먼저 읽어.
완료 기준은 [사용자 질문과 기대 결과]야. 이 범위의 구현까지 진행해줘.
코드를 작성한 뒤 관련 테스트나 실행을 선별해서 하고, 발견한 오류는 같은 범위에서 수정해.
PR에 변경 범위, 실행한 명령과 결과, 미확인 항목을 남겨줘.
```

### Codex PR 검토

```text
[PR 링크]를 main 기준으로 리뷰해줘. 먼저 PR의 검증 결과를 참고해.
이 변경의 주요 실패 가능성은 [집계 / 계약 / UI / 데이터 처리]야.
사용자 결과가 틀리거나 실행이 깨지는 문제부터 파일·줄·재현 조건을 알려줘.
필요한 경우에만 관련 엣지케이스를 추가로 확인해. 이 세션은 읽기 전용 리뷰야.
수정 요청을 받으면 합의한 브랜치와 경로에서 수정하고 관련 검증을 실행해줘.
```

### Gemini 또는 Claude 기획서 초안

```text
제주빅데이터센터 방문자용 자연어 데이터 탐색·분석 Agent의 기획서 초안을 써줘.
docs/SUBMISSION_PLAN.md의 구성과 첨부한 공개 가능 실행 증거를 사용해.
상인·도민·기업·공공 실무자의 공통 업무 흐름을 중심으로 쓰고, 출점 비교는 시연으로 보여줘.
실제 코드에서 확인한 기능과 도입 계획을 표시해. 확인 근거가 없는 수치나 성능은 쓰지 마.
15쪽 이내 분량을 전제로 페이지별 핵심 문장과 필요한 화면을 정리해줘.
```

작업 계약이 바뀌면 PR 안에서 관련 계약·예시·실행 문서를 함께 수정한다. 팀원과 새 에이전트는 다음 채팅에서 저장소의 최신 지침과 PR 링크를 읽는다. 진행 상태는 별도 공유 문서 대신 PR·이슈에 남긴다.
